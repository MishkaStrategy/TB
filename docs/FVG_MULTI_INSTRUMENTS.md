# Мультибиржевой модуль FVG

## Пользовательская модель

Один FVG-инструмент — уникальная комбинация биржи и торговой пары. Например, `BTCUSDT` на Binance и `BTCUSDT` на Bybit считаются двумя инструментами.

Для каждого инструмента сохраняются:

- биржа;
- нормализованный символ;
- выбранные таймфреймы `15m`, `1h`, `4h`, `1d`;
- статус уведомлений;
- дата создания;
- фильтры цены и размера.

Новый пользователь не получает FVG-инструменты автоматически: начальный список `symbols` пуст. Включение пользовательского FVG-модуля или повторный `/start` само по себе не добавляет `BTCUSDT` и не создаёт подписку. Инструмент начинает участвовать в расчётах и доставке только после явного добавления пользователем. Старый неструктурированный формат настроек с `enabled_chat_ids` при миграции сохраняет исторический implicit `BTCUSDT` только для уже существовавших legacy-пользователей.

Лимит составляет 10 инструментов на Telegram ID. Несколько таймфреймов одного инструмента занимают одно место. Проверка лимита и добавление выполняются внутри одной атомарной транзакции хранилища настроек. Read-modify-write транзакции JSON-настроек сериализуются между потоками и Linux/macOS-процессами через файловую блокировку, поэтому параллельный процесс не должен перезаписывать более свежее состояние `enabled=False` устаревшей копией настроек.

Глобальный `MAX_ACTIVE_SYMBOLS` также считается по уникальным комбинациям `биржа + символ`, а не по отдельным строкам таймфреймов. Поэтому включение четырёх таймфреймов одного инструмента не расходует четыре глобальных слота.

## Единая политика рыночных данных

Для Bitcoin и всех остальных активов биржевой источник FVG использует только закрытые 15-минутные свечи.

Из этих данных бот локально строит свечи старших таймфреймов:

- `1h` = 4 последовательные `15m` свечи;
- `4h` = 16 последовательных `15m` свечей;
- `1d` = 96 последовательных `15m` свечей.

Агрегация выполняется по UTC-границам таймфреймов. Свеча старшего таймфрейма считается полной только при наличии всех необходимых последовательных закрытых 15-минутных свечей. Неполный набор данных не создаёт FVG.

Таким образом:

- минутные свечи `1m` не запрашиваются;
- прямые запросы `1h`, `4h`, `1d` к биржам не нужны для FVG;
- Bitunix WebSocket подписывается только на `market_kline_15min`;
- Bitunix REST recovery запрашивает только `15m`;
- мультибиржевой poller загружает `15m` и локально рассчитывает выбранные таймфреймы;
- если в одной контрольной точке для рынка закрылись несколько таймфреймов, один общий набор `15m` используется для всех этих расчётов;
- полностью пустой набор закрытых `15m` для активного рынка считается operational failure, а не молча трактуется как отсутствие FVG.

Публичные свечи поддерживаются через единый адаптер для:

- Bitunix;
- Binance;
- Bybit;
- BingX;
- Bitget;
- Gate.

Gate Futures REST возвращает объектные candlestick rows с полями `t`, `o`, `h`, `l`, `c`; адаптер разбирает этот формат и сохраняет совместимость с массивным представлением.

Для длинного дневного lookback Bitunix использует существующую пагинацию исторических `15m` свечей, потому что один запрос Bitunix ограничен 200 свечами.

## Подтверждённые FVG

Поддерживаемые таймфреймы FVG:

- `15m`;
- `1h`;
- `4h`;
- `1d`.

На каждом таймфрейме FVG определяется по трём последовательным закрытым свечам A, B и C. Уведомление создаётся только после закрытия свечи C. Незакрытая или неполная свеча не может подтвердить сигнал.

Расписание расчётов:

- `15m` — каждые 15 минут;
- `1h` — на границе часа;
- `4h` — в 00:00, 04:00, 08:00, 12:00, 16:00 и 20:00 UTC;
- `1d` — в 00:00 UTC.

## Пред-FVG

Функция пред-FVG отключена и не используется в production runtime.

Нет:

- минутной подписки Bitunix;
- минутного REST recovery;
- предварительного multi-exchange polling;
- job `fvg-pre-control-t-minus-3`;
- пользовательской команды `/fvg_pre_alert`;
- кнопок пред-FVG в настройках и фильтрах;
- предварительных уведомлений.

Тип `PRE_FVG` и старые поля могут оставаться в низкоуровневых моделях и исторических данных только для совместимости с уже сохранённой историей. Новые события этого типа не создаются.

## Совместимость настроек

Существующие выбранные таймфреймы сохраняются. Облегчённая политика относится к источнику данных, а не к доступным FVG-таймфреймам.

- сохранённые `15m`, `1h`, `4h`, `1d` продолжают определять, какие подтверждённые FVG получает пользователь;
- `notify_pre_fvg` принудительно считается выключенным;
- фильтры применяются к подтверждённым FVG выбранного инструмента независимо от его таймфрейма;
- старые Bitunix-ключи и идентификаторы событий сохраняются, чтобы обновление не вызвало повторную рассылку.

Важно: промежуточная 15m-only версия из PR #82 интерпретировала все сохранённые таймфреймы как `15m`. Если во время работы этой версии выполнялась любая транзакция настроек пользователя, уже нормализованное состояние могло быть записано обратно. Исходный набор `1h/4h/1d` в таком случае невозможно восстановить автоматически из текущего файла — нужные таймфреймы следует выбрать заново в интерфейсе.

## Рыночные расчёты

Планировщик каждые 15 минут определяет, какие выбранные таймфреймы действительно закрылись в текущую UTC-контрольную точку. Затем он группирует расчёты по `биржа + символ`.

Для каждого рынка выполняется один общий запрос 15-минутных свечей с глубиной, достаточной для самого крупного из нужных таймфреймов. После этого `15m`, `1h`, `4h` и `1d` рассчитываются локально из одного набора данных.

Ошибка одного рынка изолирована: она увеличивает `control_point_failures`, сохраняет `last_error` и не прерывает обработку остальных рынков в том же проходе. Operational health monitor уведомляет администратора о новых `control_point_failures`.

Персональные фильтры пользователей не создают повторных запросов к бирже и не запускают повторный рыночный расчёт.

## Доставка и защита от дублей

Существующий SQLite/WAL event store и persistent outbox сохранены. Уникальный идентификатор события включает таймфрейм и биржу для новых площадок. Формат старого Bitunix ID остаётся совместимым.

Это обеспечивает:

- идемпотентную запись событий;
- отсутствие повторной доставки одному пользователю;
- сохранение очереди после перезапуска;
- повторные попытки при временных ошибках Telegram;
- прекращение повторов после постоянного отказа Telegram.

При выключенном Outbox V2 legacy-outbox перед Telegram I/O атомарно забирает due-строки под SQLite `BEGIN IMMEDIATE` и переносит `next_attempt_at` за пределы claim lease. Поэтому два параллельных bot process не могут одновременно выбрать одну и ту же пару `event_id + chat_id` и отправить один FVG несколько раз. Если процесс завершился после claim до фиксации результата доставки, запись снова становится доступна после истечения lease.

Получатель подтверждённого события выбирается только при совпадении включённого FVG-модуля, биржи, символа, выбранного таймфрейма, направления и пользовательских фильтров цены/размера.

## Telegram-интерфейс

Добавление инструмента проходит последовательно:

1. выбор биржи;
2. ввод и проверка торговой пары;
3. выбор одного или нескольких таймфреймов `15m / 1h / 4h / 1d`;
4. экран проверки;
5. явное подтверждение.

Карточка инструмента позволяет изменить таймфреймы, поставить уведомления на паузу или удалить инструмент. Настроек пред-FVG нет.

FAQ отдельно поясняет, что с бирж загружаются только 15-минутные свечи, а старшие FVG-таймфреймы строятся локально.

## Повторный аудит после проблемы на VDS

Повторный аудит линии `v1.3.3` и последующей 15m-only версии выявил несколько независимых причин, которые могли приводить к отсутствию уведомлений по другим инструментам:

1. В `v1.3.3` non-BTC `1h/4h/1d` отбрасывались до сетевого запроса, хотя интерфейс позволял выбрать эти таймфреймы.
2. В PR #82 весь active runtime был ошибочно сведён к одному целевому `15m`, а старые настройки могли быть сохранены уже в нормализованном виде.
3. Gate Futures возвращает объектные candlestick rows, тогда как прежний адаптер разбирал их как массивы и молча отбрасывал валидные данные.
4. Старое применение `MAX_ACTIVE_SYMBOLS` считало каждый таймфрейм отдельным глобальным слотом и при большом количестве подписок могло отсекать целые инструменты.
5. Bitunix имеет отдельный WebSocket/REST fallback, тогда как остальные биржи зависят от общего multi-exchange control job. Поэтому наличие уведомлений BTC с Bitunix само по себе не доказывает исправность multi-exchange polling.
6. Раньше полностью пустой распарсенный candle source мог выглядеть как обычное отсутствие FVG. Теперь это явная ошибка с health counter и журналированием.

Регрессионное покрытие включает payload-контракты всех шести адаптеров, end-to-end non-BTC `15m -> event -> recipient`, локальную агрегацию `1h/4h/1d`, сохранение всех выбранных TF внутри одного global instrument slot и продолжение обработки остальных рынков при сбое одного рынка.

## Проверка фактической версии на VDS

Файл `VERSION` недостаточен для различения промежуточных изменений в `main`: updater допускает `TARGET_REF=main` при том же `EXPECTED_VERSION`. После успешной установки точный commit SHA записывается в `/opt/fvg-alert-bot/BUILD_COMMIT`.

При расследовании production-инцидента источником истины должны быть одновременно:

- `/opt/fvg-alert-bot/BUILD_COMMIT` — точный установленный commit;
- `/opt/fvg-alert-bot/VERSION` — release version;
- `/var/lib/fvg-alert-bot/fvg_alert_settings.json` — фактические инструменты и выбранные TF;
- `/etc/fvg-alert-bot.env` — operational feature flags и лимиты без публикации секретов;
- journal `fvg-alert-bot` — ошибки `Confirmed FVG control point failed` и task overlap;
- SQLite health/background-task state — `control_point_failures`, outbox и состояние `fvg-confirmed-control`.
